# Техническая проверка персональных данных: ОКНО ЩИТ

Дата: 27 сентября 2026 года. Объект проверки — исходный код `plenki`; адрес сайта задаётся через `NEXT_PUBLIC_SITE_URL`. `medtaxi-evp` прочитан только как пример; его сервер, политика и реквизиты не подтверждают соответствие другого сайта.

Описание реализации аналитики обновлено 4 октября 2026 года: счётчик запускается автоматически, ID задаётся через окружение сборки.

Это аудит доступного frontend и точек интеграции. Доступ к рабочему API, конфигурации хостинга, журналам, договорам с обработчиками и уведомлению Роскомнадзора не предоставлен. Статус «сайт полностью соответствует требованиям РКН» по одному репозиторию подтвердить нельзя.

## Документы и настройки

`lib/legal.ts` читается серверными компонентами при сборке. Клиентская форма получает только необходимые публичные параметры. `LEGAL_VERSION = "2026-09-27"` идентифицирует текст согласия; при существенном изменении текста нужно обновить версию и сохранять старые редакции вместе с историей согласий.

| Переменная | Назначение |
| --- | --- |
| `PERSONAL_DATA_OPERATOR_NAME` | Полное наименование юридического лица или ФИО физического лица/ИП, фактически принимающего заявки. Бренд «ОКНО ЩИТ» не заменяет эти сведения. |
| `PERSONAL_DATA_OPERATOR_ADDRESS` | Достоверный адрес оператора для обращений. |
| `PERSONAL_DATA_OPERATOR_INN` | ИНН, если оператор публикует его; не подставляется из другого проекта автоматически. |
| `PERSONAL_DATA_CONTACT_EMAIL` | Дополнительный необязательный канал обращений; текущий телефон доступен и без email. |
| `PERSONAL_DATA_PROCESSOR_NAME` | Лицо, которому поручена обработка заявок, если используется отдельный подрядчик. |
| `PERSONAL_DATA_PROCESSOR_ADDRESS` | Адрес обработчика; заполняется вместе с его именем. |

`isLegalConfigured` проверяет наличие имени и адреса. Это защита от включения формы с неидентифицированным получателем, а не юридическое заключение о достаточности реквизитов или реальном соблюдении закона. Чтение страниц не блокируется. Пока реквизиты не заданы, посетителю отображается короткое сообщение о недоступности онлайн-заявок, без технических имён переменных.

В документах выбрана политика хранения заявки до завершения обращения, максимум один год с последнего взаимодействия, или до более раннего отзыва при отсутствии другого основания обработки. Это правило необходимо фактически внедрить у получателя заявок, включая удаление копий и резервных данных. Оно не свидетельствует о проверенном текущем сроке хранения.

## Что требуется перед включением приёма заявок

1. Подтвердить оператора «ОКНО ЩИТ» и заполнить достоверные реквизиты. ФИО/ИНН из `medtaxi-evp` автоматически не перенесены.
2. Подключить и проверить API именно этого сайта. Не направлять реальные персональные данные на сервер другого проекта без подтверждённой настройки получателя. Само наличие `NEXT_PUBLIC_API_URL` не доказывает готовность сервиса.
3. Подтвердить расположение баз данных, резервных копий и служб обработки в России. Проверить всю цепочку: API, CRM, почта, логи, уведомления и сторонние обработчики. Российский домен или HTTPS не подтверждает локализацию. Не пересылать заявки напрямую в иностранные мессенджеры без отдельного анализа правового основания и трансграничной передачи.
4. На стороне приёмника валидировать согласие и допустимые поля, сохранять серверное время получения, версию текста и факт согласия вместе с заявкой. Время, присланное браузером, не является достаточным самостоятельным доказательством. Не сохранять тело запроса в общедоступных логах; внедрить ограничения частоты и размера запросов.
5. Установить срок хранения и удаление. Назначить доступ к заявкам только необходимым лицам; проверить резервное копирование, восстановление, обработку отзывов и инцидентов. Если есть подрядчик — согласовать поручение обработки и отразить его в реквизитах.
6. Проверить уведомление Роскомнадзора и соответствие его данных новому сайту, целям и сервисам. Запись в реестре не проверялась: подтверждённых реквизитов оператора нет, публичный портал РКН во время проверки не ответил.

## Аналитика и cookie

### Учёт обращений в API

4 октября 2026 года frontend согласован с `conditioners-server`. Обе формы передают также путь страницы без query/hash и место формы (`inline`/`modal`). Для ОКНО ЩИТ backend проверяет согласие, версию и время, допускает пустое имя, добавляет серверное время и отправляет карточку существующему Telegram-получателю из `FREEZE_MASTER_TELEGRAM_TOKEN` / `FREEZE_MASTER_CHAT_ID`. Успешный ответ формы означает успешный ответ Telegram API; отдельное постоянное хранилище и удаление по срокам этим изменением не реализованы.

`PhoneClickTracking` отдельно от Метрики отправляет в `/api/call-clicks` номер компании из `tel:`-ссылки, путь страницы, метку кнопки, UUID клика и вкладки, время и первоначальные UTM/referrer/yclid. Источник и UUID вкладки сохраняются в `sessionStorage` (`plenki_call_session_v1`); cookie для этого механизма не устанавливаются. Backend добавляет разрешённый Origin, время и User-Agent, пишет событие в лог и отправляет уведомление в тот же чат. Номер посетителя и содержимое формы к событию клика не относятся. Событие не доказывает состоявшийся звонок. Описание добавлено в публичную политику; это описание технического поведения, а не подтверждение соблюдения всех требований к обработке.

### Яндекс Метрика

`SiteAnalytics` в корневом layout запускает счётчик автоматически через `next/script` со стратегией `afterInteractive`. Баннер выбора и настройки cookie удалены. Запуск не зависит от прежнего решения `accepted` / `declined` в `localStorage`; эта запись больше не используется. При отключённом JavaScript стандартный `noscript`-пиксель может учитывать просмотр страницы. Отдельная отметка согласия в форме по-прежнему относится к отправке заявки.

Включены Вебвизор, карта кликов, отслеживание ссылок и уточнённый показатель отказов; для ecommerce подключён `dataLayer`. Настройка слоя данных сама по себе не создаёт события покупок. Стандартный счётчик использует cookie и обрабатывает сведения о посещении; адреса страниц, их параметры и источники перехода могут попадать в его стандартные запросы.

Клиентский помощник отправляет просмотры при переходах между страницами и события `phone_click`, `social_click`, `form_success`, `form_error`. В параметры этих целей добавляются только заранее заданные метки места или канала связи; имя, телефон и содержимое формы не добавляются. На полях имени и телефона сохранён `ym-disable-keys`, исключающий их значения из записи Вебвизора. Это ограничение полей формы не отключает запись остальных взаимодействий со страницей.

ID счётчика задаётся положительным целым числом в `NEXT_PUBLIC_YANDEX_METRIKA_ID` перед сборкой. Значения по умолчанию и тестовой заглушки нет; отсутствующий или некорректный ID останавливает сборку с понятной ошибкой. После изменения ID требуется пересобрать и опубликовать `out/`.

Проверить в браузере на чистом профиле:

- Счётчик запускается с ID из окружения без предварительного выбора; ранее сохранённый отказ не препятствует запуску.
- При переходах между страницами учитываются просмотры; повторная инициализация счётчика не происходит.
- При отключённом JavaScript в HTML остаётся изображение-счётчик с настроенным ID.
- Имя, телефон и текст заявки не добавляются в параметры пользовательских целей; на полях имени и телефона присутствует `ym-disable-keys`.
- Форма не отправляется без отдельной отметки, показывает действительную ошибку при сбое API и успех только после подтверждённого ответа.
