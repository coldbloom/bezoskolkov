# ОКНО ЩИТ — oknoshield.site

Сайт на Next.js 16 с готовым HTML для всех страниц. Сборка экспортируется в `out/` и не требует Node.js на хостинге.

## Сборка и проверка

```bash
yarn install --immutable
yarn build
yarn lint
yarn test
yarn check:export
```

Перед сборкой задайте `NEXT_PUBLIC_SITE_URL` и телефоны в `.env.local` или в окружении команды сборки. `.env.example` — только образец: Next.js не загружает этот файл автоматически. Его можно скопировать в `.env.local` и заполнить нужные значения.

`NEXT_PUBLIC_SITE_URL` — единый источник адреса сайта: из него получаются ссылки, видимое имя домена, canonical, Open Graph, JSON-LD, sitemap, robots.txt и домен на картинке превью. Значение `process.env.NEXT_PUBLIC_SITE_URL` фиксируется **во время сборки** и не мешает SSG или `output: "export"`. После изменения домена или телефонов сайт нужно пересобрать и заново загрузить содержимое `out/`; изменение env на хостинге не меняет готовые файлы.

Основной контент, заголовки, ссылки, JSON-LD и юридические страницы рендерятся Server Components при сборке (SSG). Они доступны поисковым роботам без JavaScript. Это готовый сервером HTML, без необходимости выполнять SSR на каждый запрос. Клиентский код нужен только для интерактивных элементов. Модальное окно и меню подгружаются при открытии.

Загрузочный экран `components/PageLoading` включается при переходах через официальный `useLinkStatus` в `NavigationLink`. Корневой `app/loading.tsx` намеренно не используется: на проверенных Next.js 16.3.0 и 16.3.6 его Suspense-граница оставляла основной контент static export в скрытом сегменте до выполнения JavaScript. Это нарушало доступность сайта без JS. Новый загрузчик не задерживает первый показ страницы; быстрые переходы обходятся без вспышки скелетона. `check:export` проверяет отсутствие скрытых сегментов React во всех публичных страницах.

Размещайте **содержимое `out/`** в корне сайта. Хостинг должен отдавать `index.html` для URL с завершающим `/`, перенаправлять адреса без завершающего `/` на канонический URL и возвращать статус HTTP 404 вместе с `404.html` для несуществующих страниц. Проверьте MIME-типы для `.webp`, `.png`, `.xml` и `.txt`. Для ускорения включите Brotli или gzip и длительное кеширование файлов в `/_next/static/`. Не загружайте на хостинг `node_modules`, `.next` и `assets/originals`.

Перед загрузкой на VPS выполните `chmod -R a+rX out`: все публичные файлы должны быть доступны для чтения, а каталоги — для прохода пользователю Nginx. `rsync -a` сохраняет локальные права; файл с правами `600`, загруженный от `root`, будет возвращать `403 Forbidden`. Например, это может сломать логотип `/codecake.svg` в футере. Если проблема уже возникла на VPS, исправьте права командой `chmod -R a+rX /var/www/oknoshield` — этот каталог должен содержать только публичную сборку сайта.

Оригиналы двух больших иллюстраций находятся в `assets/originals/`. `yarn images:generate` создаёт AVIF и WebP шириной 480, 768, 1024, 1280 и 1536 px в `public/`. Файлы хранятся в репозитории: повторное кодирование при каждой сборке не требуется. После замены исходников выполните генератор, `yarn build` и `yarn check:export`. Компонент `ResponsiveImage` выбирает AVIF, сохраняет WebP fallback и учитывает фактическую ширину изображения; для главной картинки создаётся один responsive preload. Остальные изображения загружаются лениво. Все изображения остаются в исходном HTML.

Единый исходник логотипа — `app/icon.svg`: его использует `BrandMark` в шапке, футере и загрузчике. Макет превью `assets/og-image.svg` ссылается на тот же знак, а домен получает из `NEXT_PUBLIC_SITE_URL` при генерации PNG. Favicon и PNG для социальных сетей автоматически обновляются перед `yarn build` и `yarn dev`. Для отдельной генерации используйте `yarn brand:generate` (production env) или `yarn brand:generate --development` (development env). Скрипт использует `sharp`, поставляемый с Next.js. Локальные шрифты системы не создают запросов к внешним сервисам.

## Форма и обработка данных

Для включения отправки укажите `NEXT_PUBLIC_API_URL`, `PERSONAL_DATA_OPERATOR_NAME` и `PERSONAL_DATA_OPERATOR_ADDRESS`. Дополнительно можно указать ИНН, email для обращений и реквизиты обработчика. Не копируйте сведения другого бизнеса без проверки. Поля обеих форм доступны после загрузки JavaScript независимо от конфигурации отправки. До настройки посетитель видит доступный телефон; попытка отправки показывает явное сообщение и сохраняет введённые данные. Фиктивное сообщение об успешной отправке не показывается. На время запроса поля блокируются, после ошибки снова доступны для исправления и повторной отправки.

Форма в модальном окне и в блоке расчёта использует один модуль на всех страницах. Обязательны телефон и отдельный, изначально пустой checkbox согласия. Имя и тип объекта необязательны. Запрос: `POST <NEXT_PUBLIC_API_URL>/feedback`, JSON с `name`, `phone`, `message`, `personalDataConsent`, `consentVersion`, `consentedAt`, `page`, `formPosition`. В `message` передаются бренд, регион и тип объекта; `page` содержит текущий путь без query/hash, `formPosition` — `inline` или `modal`.

Приёмник — отдельный репозиторий `conditioners-server`, production API: `https://holodniypartner.ru/api`. Backend разрешает origin из `OKNOSHIELD_URL`, проверяет телефон и согласие, допускает пустое имя. Заявки ОКНО ЩИТ и MedTaxi используют `FREEZE_MASTER_TELEGRAM_TOKEN` / `FREEZE_MASTER_CHAT_ID`; карточка содержит фактический сайт, страницу, форму и сведения о согласии с серверным временем приёма. Успех формы возвращается после успешного ответа Telegram; ошибка доставки даёт `502`, отсутствие настроек — `503`. Содержимое HTML вместо ответа API не считается успехом. Не проверяйте реальную доставку вымышленными заявками в рабочий API.

`PhoneClickTracking` подключён один раз в корневом layout и перехватывает клики по всем `tel:`-ссылкам, включая появившиеся в модальном окне. Метка `data-call-tracking-id` различает шапку, главный блок, футер, мобильную кнопку и другие места. Нативный звонок открывается сразу. В фоне отправляется `POST <NEXT_PUBLIC_API_URL>/call-clicks` с JSON в `text/plain`, `keepalive: true`. Событие содержит номер компании из ссылки, путь страницы, отдельный UUID клика, UUID вкладки, время и первоначальные UTM/referrer/yclid. Эти сведения сохраняются в `sessionStorage` под ключом `plenki_call_session_v1`; без storage используется память страницы. Учёт кликов работает независимо от счётчика Яндекса. `202` подтверждает приём события, но не состоявшийся звонок и не доставку Telegram; ошибки уведомлений остаются в логах backend. Уведомления ОКНО ЩИТ идут в общий чат без формы перевозки пациента MedTaxi.

Для проверки соответствия фактических frontend payload и backend routers без отправки сообщений в Telegram:

```bash
node scripts/verify-api-contract.mjs /absolute/path/to/conditioners-server
```

В обоих проектах должны быть установлены зависимости. Проверка использует локальный временный HTTP-сервер и подменяет отправку Telegram.

### Публикация интеграции

1. Доставьте изменённый код `conditioners-server` на VPS в каталог серверного проекта (`/root/server` в текущей установке). В его `.env` добавьте `OKNOSHIELD_URL=https://oknoshield.site`; сохраните рабочие `MEDTAXI_URL` и настройки общего бота. Затем выполните `npm run build` и `NODE_ENV=production pm2 restart server --update-env`. PM2 должен запускать `build/index.js`.
2. В локальном `plenki` задайте `NEXT_PUBLIC_API_URL=https://holodniypartner.ru/api` и заполните имя/адрес оператора. Выполните `yarn test`, `yarn lint`, `yarn build`, `yarn check:export`.
3. Выполните `chmod -R a+rX out`, затем `rsync -avz --delete out/ root@83.222.19.84:/var/www/oknoshield/`. Назначение должно содержать только опубликованную сборку: `--delete` удаляет из него старые файлы. Nginx продолжает отдавать статику; перезапуск frontend через PM2 не нужен.

Для локальной разработки используйте отдельный локальный backend с `OKNOSHIELD_URL=http://localhost:3000` и frontend с `NEXT_PUBLIC_API_URL=http://localhost:3235/api` (если API запущен на 3235). В таком окружении используйте отдельного тестового бота или тестовый чат. Дополнительный `CALL_CLICK_ALLOWED_ORIGINS` разрешает только клики и не определяет получателя заявок формы.

Политика: `/privacy/`; отдельное согласие: `/personal-data-consent/`. Технический аудит, официальные источники и вопросы к владельцу инфраструктуры — в [docs/privacy-audit.md](docs/privacy-audit.md). Проверка frontend не подтверждает уведомление РКН, размещение баз данных и фактические процессы обработки.

## Аналитика и cookie

`SiteAnalytics` включён в корневой layout. Перед сборкой задайте `NEXT_PUBLIC_YANDEX_METRIKA_ID` в `.env.local`: положительный целочисленный ID счётчика. Значения по умолчанию в коде нет; отсутствие или некорректное значение останавливает сборку с сообщением об ошибке. ID фиксируется в готовом HTML и JavaScript, поэтому после его изменения нужны новая сборка и загрузка `out/`.

Очередь Метрики и `init` создаются автоматически через `next/script` со стратегией `afterInteractive`. Загрузка внешней библиотеки начинается после события `load` в свободное время браузера (`requestIdleCallback`, timeout 2000 мс; fallback `setTimeout`). Цели и переходы, случившиеся раньше, сохраняются в очереди. Это действует на всех страницах и не требует взаимодействия пользователя. Запуск не зависит от принятия или отклонения аналитики; баннера выбора и кнопки настроек cookie нет. При отключённом JavaScript работает стандартный `noscript`-пиксель. Включены Вебвизор, карта кликов, отслеживание ссылок и уточнённый показатель отказов; для ecommerce подключён `dataLayer`. Само подключение `dataLayer` не создаёт события покупок.

Клиентский помощник учитывает переходы между страницами и цели `phone_click`, `social_click`, `form_success`, `form_error`. В параметры этих целей попадают только заранее заданные метки; имя, телефон и содержимое формы туда не добавляются. На полях имени и телефона сохранён класс `ym-disable-keys` для исключения их значений из записи Вебвизора. Стандартный счётчик отдельно собирает сведения о посещении, включая адрес страницы и источник перехода, и использует cookie. Прежняя запись выбора аналитики в `localStorage` больше не управляет запуском.

## SEO и публикация

Метаданные главной, canonical и настройки Open Graph/Twitter собраны в `lib/seo.ts`; отдельные описания регионов — в `lib/regions.ts`. Главная и `/regions/yug-rossii/` используют один набор SEO-данных с canonical на `/`. Остальные региональные страницы ссылаются на собственные адреса. `check:export` проверяет уникальность метаданных и согласованность canonical, OG, sitemap и JSON-LD в готовом HTML.

Для подтверждения прав на сайт можно задать `GOOGLE_SITE_VERIFICATION` и `YANDEX_SITE_VERIFICATION` перед сборкой. Нужны значения `content` из метатегов собственных кабинетов, без HTML-разметки. Подробный анализ, группы запросов и порядок проверки после публикации — в [docs/seo-audit.md](docs/seo-audit.md).

Региональные страницы доступны для индексации, но для сильного ранжирования их нужно дополнять настоящими локальными сведениями и примерами работ. Скорость и корректная разметка не гарантируют позиции в поиске.

Если старый домен уже использовался, настройте постоянные 301-редиректы на соответствующие пути домена из `NEXT_PUBLIC_SITE_URL`, подтвердите новый домен в кабинетах поисковых систем и отправьте sitemap. Это настройка хостинга, DNS и кабинетов; `output: "export"` не выполняет серверные redirects/headers из `next.config.ts`.


## Скорость главной и Nginx

Проект сохраняет `output: "export"`: основной контент, заголовки, метаданные и JSON-LD рендерятся во время сборки и входят в `out/`. Клиентские формы, меню и обработчики аналитики не переводят страницу в CSR. SSR на каждый HTTP-запрос и ISR в этой конфигурации не используются. Перед публикацией `yarn check:export` проверяет видимый HTML, метаданные, телефонные ссылки, AVIF/WebP и отсутствие двойного preload главной картинки.

На VPS 4 октября 2026 года HTML отдавался с gzip, а проверенные CSS/JS — без сжатия и явного кеширования. Подготовлен [deploy/nginx-performance.conf](deploy/nginx-performance.conf), который подключается **внутри существующего HTTPS-блока `server` для `oknoshield.site`**. Он включает gzip для текстовых ресурсов, годовой immutable-кеш файлов с хешами из `/_next/static/`, часовой кеш обычных изображений и перепроверку HTML/RSC после обновления. AVIF получает корректный MIME-тип даже при старом `mime.types`.

На VPS создайте каталог, если его нет:

```bash
sudo mkdir -p /etc/nginx/snippets
```

Из локального каталога plenki загрузите snippet:

```bash
scp deploy/nginx-performance.conf root@83.222.19.84:/etc/nginx/snippets/oknoshield-performance.conf
```

В `/etc/nginx/sites-available/oknoshield`, в блоке с `listen 443 ssl`, добавьте одну строку рядом с `root` / `index`:

```nginx
include /etc/nginx/snippets/oknoshield-performance.conf;
```

Существующие сертификаты, `server_name`, `root /var/www/oknoshield`, `location /` и `error_page` сохраняются. Snippet подключается один раз; если аналогичные `gzip` или asset locations уже добавлены в этот же блок, объедините настройки. Если в конфигурации используются дополнительные `add_header`, учитывайте указанное в snippet правило наследования Nginx.

Примените на VPS:

```bash
sudo nginx -t && sudo systemctl reload nginx
```

Затем опубликуйте новую сборку обычной командой из раздела деплоя. В ответах CSS/JS должны появиться `Content-Encoding: gzip` при `Accept-Encoding: gzip`; у файлов `/_next/static/` — `Cache-Control: public, max-age=31536000, immutable`. У `/hero-768.avif` ожидаются `Content-Type: image/avif` и кеш на 3600 секунд. Обновление одного `out/` не применяет настройки Nginx.

Измерения и границы проверки сохранены в [docs/verification.md](docs/verification.md). Лабораторный балл Lighthouse не является гарантией скорости у каждого посетителя или позиции в поиске.
